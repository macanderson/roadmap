Specification

Steering repo

Every workspace gets one repository that holds what its agents are told and which tools they may call. Oxagen creates it with the workspace, lays it out, holds its settings, and publishes it on every merged steering PR. This spec builds on steering records v1: it moves .oxagen/ to the repository root and adds tool servers, agents, policies, memories, and the settings Oxagen enforces.

Summary

Changes from v1

Steering records v1 stands: one Markdown file per record, YAML frontmatter, the kinds, the forces, the two-pass hash, and the six checks. What changes is the repository around the records.

  • Decided Oxagen creates the repository. Every new workspace gets a private repository in the organization's GitHub organization or GitLab group. Customers no longer choose which repository holds steering.
  • Decided The root is the old .oxagen/. steering/, tools/servers/, and workspace.toml sit at the top of the repository.
  • Decided Runs follow the agent's workspace. The workspace an agent is bound to supplies the steering, rules, and tools for its runs.
  • Decided A code repository can belong to many workspaces.
  • Decided Oxagen holds the settings. Oxagen sets the branch and merge rules so it can always merge from the web app. When someone changes them, every pull request fails at once and Oxagen warns the workspace.
  • Decided Pull requests stay the only way in. A change to configuration or steering takes effect only through a merged pull request.
  • Decided A new name. The main repository becomes the steering repo, to match steering records and the steering PR.
  • Decided New folders. tools/servers/ for every MCP server and its imported tools, policy/, and steering/memory/, and proposals/ goes.
  • Decided Four new record fields (repos, tools, skills, and description on every kind), and an optional token budget on always-on records. A workspace that sets no budget inherits Oxagen's default.
  • Proposed Every memory names its author. A stored memory records the agent and run that wrote it, and a promoted memory keeps the agent in provenance.agent.

Scope

Day one

The smallest version of agents, subagents, and tools that ships, with the rest waiting until customers ask. Mac set it on 2026-09-26.

Ships

  • Agents. An agent is an operator, a harness, and a runtime. Each has a file in agents/ that names the three, and Cedar sees it as the principal Agent. Decided
  • Tools. Every agent in a workspace gets the workspace's imported tools and its harness's built-in tools. Decided
  • Least privilege. Cedar policies in policy/ narrow what an agent may call, by the agent, its operator, harness, or runtime, and the tool's classification. Decided
  • Built-in tools. Cedar decides a harness's own tools too, in one vocabulary for every harness: builtin__shell is Claude Code's Bash and Codex's shell. The pre-tool hook asks for the decision. Decided for one vocabulary, Proposed for the names. See Built-in tools.
  • Separation. Teams that must not share tools use separate workspaces. Decided
  • Subagents. A Cedar policy on the skill a subagent runs limits it, such as a reviewer that may only read. See Subagents. Proposed
  • Context size. Studio suggests search mode for a server whose definitions pass its budget, and an agent then sees three tools for that server instead of every definition. The budget check warns when the workspace's direct-mode total grows too large. See Finding tools. Proposed

Waits

  • Named toolbelts in tools/toolbelts/, and a toolbelt per agent or per skill.
  • A budget per agent. The workspace's limits in workspace.toml apply to every run.
  • An environment per agent. A server's calls use its sandbox.

Holes

  1. No Cedar evaluator exists. Decision rules run in the zod engine in packages/rules, and no lane built an evaluator until this change. Lane S12 builds it for the gateway and the pre-tool hook, and every item above depends on it.
  2. The hook decides on the machine. Built-in tools never reach the gateway, so the compiled policies ride in the signed host bundle, and the hook evaluates them there. Offline, it decides from the cached bundle, as the hook does today.
  3. A forbidden tool stays in the list. An agent sees every workspace tool, including one a policy forbids it, and the call is refused with the rule's reason. Hiding such a tool needs the gateway to test each tool for the agent when a run starts. Proposed for later.
  4. Subagent calls. A helper's limit holds only on a harness that says which skill made each call. Elsewhere the call gets the main agent's rules, and the Skills screen warns. Decided (Mac, 2026-09-26)
  5. New agents. A policy names an agent by its file, so an agent enrolled before its file merges runs under the workspace's policies alone.
  6. Many workspaces. A person on two teams switches workspace, and each workspace's runs and spend are its own. Records both teams need go in the organization repo, <org>/oxagen.

Operators

Oxagen assumes every operator follows the conduct rules of their job, and adds no controls aimed at an operator who breaks them. The tier words still say only what a run's record can show. Decided (Mac, 2026-09-26)

Formats

File formats

Four formats, each with one job. A file a standard defines keeps that standard's format. Decided

FormatExtensionUsed forRules
Markdown with YAML frontmatter.mdEvery steering record, every SKILL.md, every memoryThe v1 rules: a strict YAML subset with no anchors, aliases, tags, or second document, then a CommonMark body. Decided
TOML 1.0.tomlworkspace.toml, governance.toml, agents, servers, and MCP Studio's api.toml and tools.tomlThe first line is #:schema https://oxagen.sh/schemas/<id>.json. Unknown keys are an error.
JSON Lines.jsonlThe ledger, policy tests, recorded API callsOne JSON object per line, UTF-8, keys in a fixed order. Lines are only ever added.
Standard formats.cedar .yaml .jsonCedar policies, OpenAPI documents as the API owner publishes them, W3C design tokens inside a design-system skillOxagen reads them and never rewrites them.
  • TOML for configuration because it is what the code writes today, and because a bare word in TOML is a syntax error. YAML reads no as false and 2026-09-25 as a date without a word of warning.
  • No YAML or JSON configuration files. YAML appears only as frontmatter and inside OpenAPI documents. JSON has no comments and spends more tokens on quotes and braces for the same content.
  • Editors complete every key. Taplo and Even Better TOML read the #:schema line, and each record's schema field names its JSON Schema.
  • One encoding. UTF-8, LF line endings, no byte-order mark, and a final newline. Oxagen's .gitattributes pins * text=auto eol=lf.
  • Size limits. 256 KB for a record or a TOML file, 1 MB for an asset in a skill folder, and 25 MB for an OpenAPI document.

Mentions. A record's body can @mention a skill or a tool, so a rule sends the agent to a fixed procedure or a deterministic function: "Prorate with @skill:a-intel.billing.prorate" or "Compute the amount with @tool:billing__calculate_refund_amount". Decided that rules support them (Mac, 2026-09-26). Proposed for the syntax and the rules below.

  • A mention resolves by lineage or by tool name, so moving a folder never breaks it.
  • When the record reaches a request, a mentioned skill's index line comes with it, and the agent reads the body on demand.
  • The references check fails a mention that resolves to nothing.
  • A mention points the model at something and grants nothing. The tools field decides when the record loads, and Cedar decides the call.

Records and policies. A record tells the model what to do. A Cedar policy decides a tool call whatever the model does, and a record never grants authority. When the gateway can decide a rule from a tool call and its inputs alone, the rule gets a policy, and a record explains it to the agent so it asks first instead of hitting the wall. Other rules, such as how to prorate or when to escalate, stay records only. Proposed

Example records

One example of each kind, all from the a-intel workspace. Each opens in a window.

Business rule

A rule of the business the agent must follow. Reaches every request at must.

Code rule

A rule about how code is written. Loads when the run touches a matching file.

Constraint

A gate with an effect of require or forbid. Never grants authority.

Procedure

Steps to follow for a task. Reaches a request when the task fits.

Fact

Something true about the work. Loads when it fits the request.

Ontology entry

A fact that defines one entity or term. Definitions only.

Style preference

How the team likes things written or built.

Skill

A packaged capability with its own files. The index line always, the body on demand.

Memory

Something an agent learned in a run, promoted by a memory PR.

Cedar policy

Never sent to the model. The gateway decides each tool call with it.

Imported tool

One tool an MCP server offers, imported with its risk classification.

Reflection

A memory the agent writes at the end of a run, with grades for the work and its tools. It stays in Oxagen.

Ontology entry

An entity is a fact with a short definition, its states, and the tools that touch it. tools keeps it out of runs that cannot call those tools.

Brand and design system

A brand or a design system is a skill folder. A short preference carries the two or three rules every request needs, and the skill carries the rest for the requests that write copy or build UI. The pattern keeps the always-on cost to a few dozen tokens.

Function tools

A rule can point an agent at a deterministic function, such as calculate_refund_amount, instead of leaving arithmetic to the model. A function tool would be a server folder with a functions source beside the URL and OpenAPI sources, so it gets the same classification, lock, and Cedar decisions as any other tool. Proposed

Function code runs in a sandbox in Oxagen's cloud, and TypeScript is the first language it supports. A customer that wants the code on its own infrastructure builds a REST endpoint instead and connects it as a server from its OpenAPI document. When the endpoint sits behind a private network, MCP Studio's relay reaches it. Decided (Mac, 2026-09-26)

Subagents

A subagent often needs fewer tools than the run that starts it, such as a reviewer that may read code and write nothing. Day one, a Cedar policy on the skill it runs sets that limit. Proposed

  • The skill in context. When the harness says which skill a subagent runs, the hook or the gateway adds it to the request as context.skill. A record whose skills list holds that skill reaches the request.
  • Read only by class. A policy forbids any call whose side effect is not read for that skill, so a new write tool never slips in. Built-in tools carry a classification too, so the same rule covers builtin__write_file and builtin__shell.
  • What the model sees. When a harness has its own tool list for a subagent, such as the tools field of a Claude Code subagent, Oxagen can fill it when it delivers the skill. The list trims what the model sees, and Cedar decides the call.
  • Knowing the caller. A skill's limit holds only on a harness that says which skill made each tool call. On a harness that does not say, the call is checked against the main agent's rules, and the Skills screen warns, harness by harness, where the limit does not hold. Decided (Mac, 2026-09-26)
  • Later. A skill's own toolbelt field, with named toolbelts.

Scope

Scope and binding

  • Decided The agent's workspace governs the run. A session's workspace already comes from its host's enrollment, so the code follows this today. This replaces the 2026-09-25 rule that scope comes from the origin checkout.
  • Decided A code repository can be linked to many workspaces. The binding role main becomes steering. A steering repo belongs to exactly one workspace and is never linked. The exclusivity index and trigger stay, now on steering.
  • Decided What a run receives. Workspace records from its agent's steering repo, repository records whose repos names the run's working repository, and organization records. A narrower record may narrow what a wider one allows. It never widens it (v1).
  • Decided Linking is a steering PR. The Link button opens a steering PR that adds the repository to workspace.toml. The binding follows the merge.
  • Decided Code repositories hold no committed Oxagen files. A repository in two workspaces cannot hold two sets of skills, so v1's delivery route that writes .claude/skills/ and .cursor/rules/ into the code repository goes. Skills reach the harness at session start, in a location outside the repository, and records reach it through the cloud gateway.
  • Decided Organization records. Oxagen creates <org>/oxagen with the organization for scope: organization records. Every workspace inherits them, so a rule shared by 40 workspaces is written once.
  • Decided Unlinked repositories. A run on a code repository not linked to its agent's workspace is allowed. Its cost goes to that workspace, and the run record flags the repository as unlinked, so an agent that touches several repositories keeps working.

Drift

Settings drift

When someone changes a prescribed setting, Oxagen notices within seconds, fails every pull request, and stops publishing until the setting is back. Decided for the outcome and the mechanism below (Mac, 2026-09-26).

Steering PR

Steering PR flow

v1's flow stands: open, check, review, merge, publish, retire. These steps change it so Oxagen is the only merger and every merge is checked against the main it lands on.

  1. Open.

    From the web app, an agent's MCP tool, MCP Studio, the curator, or a clone. The branch starts with the top-level folder it changes: steering/, tools/, agents/, or policy/. Two changes are exceptions. A change to workspace.toml, a file at the repository root, uses workspace/. A memory PR changes steering/memory/ and uses memory/. A person's steering PR holds one record, as in v1. A memory PR and a server PR hold many files. Decided (Mac, 2026-09-26)

  2. Check.

    Oxagen runs the checks below and posts one required check, Oxagen steering, with each result inside it. Decided (Mac, 2026-09-26)

  3. Review.

    The web app has Approve and Merge buttons on every steering PR, and both act through Oxagen Steering. In solo mode there is no approval step: Merge is the only action, and a merged steering PR counts as approved. In every other mode a steering PR needs an approval, then a merge. The workspace owner, in any mode, may merge as in solo mode. A custom role can grant the same right with one checkbox, and no other role has it, organization admins included. Decided (Mac, 2026-09-26)

    The checkbox reads Merge without review, and the permission is merge_without_review. Proposed

    The required check still has to pass for anyone who merges without an approval, and the ledger line and the merge commit record who did it. A reviewer approves in Oxagen or with a GitHub or GitLab review from an account linked to an Oxagen member, and governance.toml can route folders to reviewer groups. The host's branch rules require no reviewer, so Oxagen enforces the approval. Proposed

  4. Queue.

    Merge, or auto-merge once approved, puts the pull request in the repository's queue. Oxagen merges one at a time. When main moves, the next pull request is brought up to date and checked again, so the budget and conflict checks judge the main it will land on. Proposed

  5. Stamp.

    At the head of the queue, Oxagen pushes one commit to the branch that writes id and hash into changed records and adds the ledger line. Only the head of the queue is stamped, so no two branches append to the ledger. Decided (Mac, 2026-09-26)

    Oxagen squash-merges at the stamped SHA. The commit message carries trailers: Oxagen-Approved-By, Oxagen-Checks, and Oxagen-Version. Today for the squash merge

    Oxagen builds the next published version from the merged tree, switches new model requests and tool calls to it at once, and records a deployment to steering. Decided (Mac, 2026-09-26)

    Each published version gets the next number for its workspace, starting at 1 when the repository is created. A number is never reused, so a revert is a new number. Decided (Mac, 2026-09-26)

Memory

Memory and reflection

Agents learn things in runs that the next run should know. Oxagen captures those lessons in Oxagen's database, where writing is cheap and fast, and reaches the repository only through a steering PR, where a person reviews what every agent will be told. The rule: the repository holds what steers, and Oxagen holds what happened. Decided

Today memories are Neo4j :AgentMemory nodes behind the knowledge-graph flag, recalled only by the in-app agent, and the reflector is not built (ADR-061 §3, ADR-097). Today

Lifecycle

  1. Observe.

    A frame in the run shows something worth keeping: a failed tool call, a person's correction, a retry loop, or a policy denial.

  2. Capture.

    The agent calls remember during the run, or writes a reflection at the end. Both are memories, stored in Oxagen with the frame as evidence and with the agent and run that wrote them. Memories agents write elsewhere arrive too: the code repository check finds them in pull requests, and the local gateway reads each harness's memory locations on the machine.

  3. Propose.

    Once a day, or when 20 memories wait, the curator keeps what is worth keeping, merges duplicates, drops what an active record already says, and opens one memory PR on a memory/<date> branch. A kept item lands as a memory, or as a rule or a fact when that fits better. Most memories never reach a PR.

  4. Review.

    A reviewer merges the PR or drops single memories from it. Oxagen pushes a commit that removes a dropped file and records the rejection, so the same lesson returns only with new evidence.

  5. Publish.

    A merged memory is a steering record of kind memory under steering/memory/. Recall can add it to any request its repos, tools, skills, and applies_to fields match, whichever agent sends it.

  6. Recall.

    The cloud gateway adds up to five relevant memories to a request, 800 tokens at most, and lists them in the request's manifest.

  7. Retire.

    Oxagen counts each memory's recalls and outcomes in its database, never in the file. A memory a reflection contradicts, or that no run recalled in 180 days, is proposed for archiving in the next memory PR.

Memory author

Oxagen stores each memory as memory/v1, with the agent that wrote it and the run it came from. The agent is named by the lineage its agents/<name>.toml file gives it. Proposed

  • Oxagen sets agent and run from the authenticated run. The inputs to remember and reflect have no agent field, so an agent cannot write a memory under another agent's name.
  • A memory the local gateway reads from a harness's memory folder gets the agent that enrollment recorded for that harness on that machine. Its run is null.
  • A memory the code repository check finds in a pull request gets the agent and run that opened the pull request, when Oxagen recorded that run. Otherwise both are null, and the memory steers nothing until a person reviews it.
  • A reflection carries agent and run the same way, and each lesson in it takes both from the reflection.
  • When the curator promotes a memory, it copies agent into the record's provenance.agent.

capture is remember, pull_request, or local_gateway. agent and run are null only where the list above allows it.

Tokens

Token efficiency

An always-on record is paid on every model request of every run it reaches. The design keeps that set small and byte-stable so it caches, and makes everything else load on demand. A workspace never has to set a budget. Decided (Mac, 2026-09-26)

It is optional: a workspace that sets nothing inherits Oxagen's default of 4,000 tokens, a workspace can set its own in governance.toml, and "off" turns the check off. What finding grants

Nothing. Finding a tool, in the list or by search, grants no right to call it. Cedar decides every call. On day one every agent holds every imported tool, so a search returns a tool a policy forbids the agent, and the call comes back refused with the rule's reason. Hiding such a tool is a later step (Day one, Holes).

Records and mentions

  • tools field. A record's tools target matches by tool name, so it works the same in both modes. On day one every agent holds every imported tool, so the target matches whenever the tool is imported. It narrows once named toolbelts arrive.
  • @tool: mentions. A search-mode tool is absent from the agent's list, so a mention of it would name a tool the agent cannot see. Publish renders each mention for the tool's current mode: billing__calculate_refund_amount in direct mode, and "call billing__call with tool calculate_refund_amount" in search mode. A mode change then needs no edit to any record. Proposed
  • steering_search. Finds records and skills only. Tools come from the tool list or a server's own search tool.

Workspace total

Each server's budget bounds that server alone. Since every agent gets every imported tool on day one, the direct-mode definitions of all servers add up on every request. The budget check also totals them and warns past [tools] definition_budget in workspace.toml, 20,000 tokens by default, naming the largest servers to switch to search mode. It only warns, like the always-on budget, and a workspace never has to set it. Proposed

The names follow the rename in #4325. Today's tools are propose_record, open_context_pr, and merge_context_pr.

Migration

Migration

With no customers, the move is one pass per workspace. Proposed

  1. Provision.

    Oxagen creates each workspace's steering repo.

  2. Import.

    One steering PR in the new repository copies .oxagen/ from the old main repository into the new layout, and converts v0.1 TOML records to v1 Markdown as the v1 spec's migration says.

  3. Clean up.

    After it merges, one pull request on the old main repository removes the committed .oxagen/ files. The gitignored machine-local files stay.

  4. Relink.

    The old main repository becomes a linked repository of the workspace.

In macanderson/oxagen, about 17 constants hold the .oxagen path. The build replaces them with one module. They are in context.steering.file.ts:21, context.steering.policy.ts:7, contracts/context.governance_mode.set.ts:68, repository.tree.get.ts:39, repository.init_pr.open.ts:55, context.steering.published.get.ts:45, skill-config.service.ts:8, contracts/agent.definition.commit.ts:29, contracts/skill.propose.ts:26, skills.ts:26, apps/cli/src/commands/pull.ts:113, and apps/app/src/data/live/mappers/steering.ts:250. steering-freshness/src/settings.ts:35 and mcp-config/src/resolve.ts:46 name the machine-local folder in a code checkout and stay. Stella's loader (stella-records/src/ingest/record.rs), the i18n messages, and the docs change too. A new ADR replaces the main-repository parts of ADR-099.
